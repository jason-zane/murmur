# Mailbox identity and rich message release contract

Mailbox appearance is account instrumentation: the email address remains visible in navigation, all-inbox badges, reader and composer. Concourse's interaction accent remains unchanged. Five approved colours (indigo, teal, violet, amber, slate) and built-in initials/mail/work/personal/no-icon options never infer an account's role or change sender permissions. Arbitrary remote logos and logo services are not implemented.

`mail_preferences.identity_colour` / `identity_icon` are optional enum-constrained text columns. NULL colour uses the UTF-8 account-ID byte sum modulo the ordered five-colour palette, shared with native tests; NULL icon means initials. Existing accounts and old native payloads remain readable. The existing first-party editor/ownership gates and SELECT-only owner policy remain unchanged. POST accepts a strict preference patch and supplies verified owner/connection IDs itself. Omitted fields are not written; old signature-only clients preserve appearance, appearance-only native writes preserve signatures. The operation does not refresh provider tokens, invoke Gmail or dispatch mail. Concurrent changes to the same preference use last-writer semantics; this is not document CAS.

Web preferences keep separate unsaved edits while switching accounts, block repeated saves synchronously, retain edits on errors and ask before discarding. Native preferences guard duplicate saves and ignore cancelled/account-switched acknowledgements. Confirmed native appearance is cached within the existing owner-specific mail cache. No colour or icon replaces the visible address.

The synthetic web transport persists only under its dedicated browser fixture key. It never falls back to network APIs; its UI states this. Invalid fixture storage is preserved and fails rather than acknowledging a save. A corrupted appearance fixture does not block unrelated note operations.
