## Findings

No material privilege bypass was found within this operation. The migration remains unapplied. These boundaries were checked against the actual migration, existing `is_murmur_editor` / `put_session` functions, HTTP handlers and local API schema configuration:

| Boundary | Finding and evidence |

| Definer helper | Public write wrapper is invoker; the private helper alone uses definer rights. Its explicit empty search path and qualified application relations prevent schema-name substitution. It independently checks UID, editor status, ownership, source revision, strict document fields and every excerpt before mutation. No owner argument, dynamic SQL, token, provider, dispatch or service-role path exists. |
| Execution privileges | PUBLIC/anon execute rights are revoked, authenticated execution is explicit, and new private functions have default PUBLIC execution revoked. Authenticated schema USAGE permits the public wrapper to call the helper; it does not bypass helper checks. The fixture calls the helper directly with a connected-AI claim and confirms denial. `concourse_private` is absent from configured exposed API schemas (`public`, `graphql_public`). The helper's definer/search-path metadata is asserted in PostgreSQL. |
| Existing editor policy | Editor status uses the verified request UID/JWT and the first-party client whitelist. Running this function under helper definer rights does not mint or change JWT claims. Real token validation is the HTTP/Auth boundary; hand-set rollback fixture claims prove policy behaviour, not issuer authenticity. No Auth/security configuration was changed. |
| Source update/delete race | The helper takes SHARE on the owned source before validating revision/evidence, blocking concurrent UPDATE/DELETE until its transaction ends. After a waiting source lock, it checks the returned revision. A later note edit preserves the historical draft but API reads invalidate effective approval. Every display consumer must compare source revision; raw table `reviewed` remains historical. |
| Draft create/update race | Source SHARE → user/note advisory transaction lock → draft FOR UPDATE serialises missing-row creation and existing updates. Identical payload retries return the same version; different payloads require the current expected version. PostgreSQL READ COMMITTED is assumed. Higher-isolation serialization failures must preserve recovery and require refresh/retry. Advisory hash collisions can reduce concurrency, not bypass ownership or CAS. |
| Lock ordering | Existing single-note `put_session` takes its separate note advisory lock then source FOR UPDATE; it never waits on a follow-up lock. The follow-up operation never waits on that note advisory lock, so no inverse dependency was found between these single-operation paths. Arbitrary multi-note/manual SQL transactions can still create deadlocks; actual concurrent integration remains required. |
| Read/source snapshots | GET obtains draft and note version in one stable SQL statement. The UI's later source fetch validates metadata/document identity and checks version consistency, repeating the snapshot once if necessary. PUT checks current source again, so a later edit produces 409 rather than stale approval. |
| Semantic trust | An exact quote proves source lineage only. User-written body text is not semantically validated. The UI states this and requires human review. There is no execution or sending consequence attached to `reviewed`. |

## Independent review corrections after deb77d5

The parent's independent review identified four functional boundary issues, now corrected locally: direct owner source writes could retain a reviewed revision; the API was not gated with the Notes UI; oversized excerpt replacement could exceed recovery limits; and status/version flags treated clean refreshes as dirty conflicts. Regression tests first reproduced the latter three. The expanded real PostgreSQL rollback fixture now exercises the direct-write freshness paths.

The proposed migration now installs `concourse_private.enforce_session_revision` before the draft table. This helper is **security invoker**, performs no queries or dynamic SQL, has an empty search path and denies PUBLIC/anon/authenticated direct EXECUTE. Trigger invocation remains available under existing table grants; RLS still controls whose rows can change. INSERT starts at 1; document/title/start/deletion changes advance the locked row exactly once; version-only changes are ignored; identity changes are rejected; content reverts and restoration never reuse approval versions. Revision overflow fails before mutation. The normal `put_session` assignment and equal retry behaviour remain intact in actual role tests. This does not repair or redesign direct-write revision-history capture.

This trigger acquires no extra relation/advisory locks. It runs while PostgreSQL already holds the source row lock, so the source SHARE → follow-up advisory → draft FOR UPDATE ordering is unchanged. No new inverse lock dependency or elevated privilege was found in this static recheck. Sequential rollback role tests are not proof of concurrent interleavings or real-token validation. The parent reviewer's amended-code recheck confirmed these four corrections. Actual issuer/concurrency checks remain required.
